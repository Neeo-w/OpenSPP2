# نظام التوثيق الهرمي الديناميكي — توثيق التنفيذ ومراجعته

هذه الوثيقة تشرح ما تمّ بناؤه فعلاً في `alkathiry_base` لتلبية **سيناريو الهرميات
الديناميكية متعددة الهرميات (الإصدار 2)**، وتقابل كل بند من المواصفة بما نُفِّذ، مع
بيان نقاط **إعادة الاستخدام** و**الانحرافات المقصودة** عن المواصفة.

> الفلسفة: **محرك هرمية واحد** يخدم كل البُنى (قبلية / عُقّال / نقابية / إدارية)، لا
> يتغيّر بينها سوى المصطلح. لا تكرار، ولا اعتماد على وحدة `hr`، وإعادة استخدام أقصى
> ما يمكن من البنية القائمة في OpenSPP.

---

## 1. مقابلة النماذج: المواصفة ↔ التنفيذ

| نموذج المواصفة | المُنفَّذ | ملاحظة الدمج / الانحراف |
|---|---|---|
| `doc.hierarchy.type` | **vocabulary** `urn:alkathiry:vocab:position-track` | أُعيد استخدام مفردات النوع بدل نموذج مستقل (قبلية/عُقّال/نقابة/لجنة/منظمة) |
| `doc.hierarchy` | `doc.hierarchy` | كما هي: `name`, `type_id`, `country_id`, `level_ids`, `active` |
| `doc.level` | `doc.level` | كما هي + `_parent_store` (لعرض المخطط) + `country_id` محسوب من الهرمية |
| `doc.documenter` | `doc.documenter` | `role` صار `role_id` (vocab)؛ `geo_node_id`→`area_id` (spp.area)؛ `job/department` (vocab) |
| `doc.committee` | **`alkathiry.organization`** (نوع=لجنة) | أُعيد استخدام نموذج المنظمات وأعضائه بدل نموذج لجنة مستقل |
| `doc.geo.node` | **`spp.area`** | شجرة OpenSPP الجغرافية (دولة→محافظة→مدينة→حي، `parent_path`) |
| `doc.request` | `doc.request` (mail.thread) | `citizen_id`→**`res.partner`** (مُسجّل) بدل `res.users` |
| `doc.request.route` | `doc.request.route` | + حقل `state` لكل خطوة (pending/current/approved/rejected) |
| `doc.request.log` | `doc.request.log` | كما هي + إجراء `certify` |
| امتداد `res.partner` | `alk_user_type` | الموقع/الدولة موجودان أصلاً (`area_id`/`country_id`)، فلم يُكرَّرا |
| `hr.job` / `hr.department` | **vocabularies** `job` / `department` | بدائل خفيفة (وحدة hr غير مثبّتة في OpenSPP) |

**الخلاصة:** كل نماذج المواصفة موجودة وظيفياً؛ ما اختلف هو إعادة توجيه الجغرافيا
واللجنة والمنصب/القسم إلى بنية OpenSPP القائمة بدل إنشاء نماذج موازية.

## 2. الهرمية والديناميكية (البناء بلا كود)

### 2.1 المحرك العام `doc.level`
المستوى **وعاء عام واحد**؛ خاصيته `kind` مجرد تصنيف يختاره الأمين:

```
kind = position | department | committee | region | custom
```

أياً كان النوع، **الخيار الهرمي حاضر دائماً**:
- `sequence` — الترتيب الإجباري (10، 20، …).
- `parent_level_id` — المستوى الأعلى التالي (به يُبنى المسار ويُرسم المخطط).
- `documenter_ids` — أعضاء المستوى الذين يختار المستفيد منهم.

تصنيفات اختيارية لكل مستوى/عضو (كلها معاد استخدامها):
- `area_id` → **spp.area** (مكان)، مع `geo_level` للفلترة بالاحتواء.
- `committee_id` → **alkathiry.organization** (لجنة).
- `job_id` / `department_id` → مفردات خفيفة.

`_parent_store` + `parent_path` يتيحان **عرض المخطط التنظيمي** (hierarchy view)
من الأعلى للأسفل، وكشف الحلقات الدائرية عبر قيد `_check_no_level_cycle`.

### 2.2 الهرمية `doc.hierarchy`
نسخة مرتبطة بدولة، تجمع `level_ids`. يبنيها الأمين بالكامل من الواجهة:
نوع + دولة + مستويات (لكلٍّ `kind` و`parent_level_id` وأعضاء). عدد غير محدود من
الهرميات، وكلها تتشارك نفس المنطق.

### 2.3 القمة المشتركة (Global)
مستويان مزروعان بـ `is_global=True` وبلا هرمية:
- `level_secretary_general` (seq 1000) — الأمين العام، قمة كل المسارات.
- `level_secretary_committees` (seq 900) → أبوه الأمين العام.

يُلحقهما **باني المسار تلقائياً** بنهاية أي مسار، فتنتهي كل الهرميات عند **نفس**
السجل المشترك (سجل واحد لكل الدول والهرميات).

### 2.4 الاستنساخ حسب الدولة
معالج `doc.hierarchy.clone`: ينسخ الهرمية ومستوياتها وروابط `parent_level_id`
إلى دولة أخرى (الأعضاء يُفرَّغون افتراضياً) — فتُعاد بنية السعودية مثلاً لمصر بنقرة.

## 3. الفلو (سير العمل) وطريقة العمل

### 3.1 بناء المسار — معالج `doc.route.builder`
خوارزمية المواصفة (§11-أ) منفّذة حرفياً في `action_build`:

```
ابدأ من start_level_id (مستوى المستفيد/المقدّم)
node = start_level_id.parent_level_id
بينما node موجود وغير مزور:
    members = node.eligible_documenters(منطقة المستفيد)   # فلترة بالاحتواء إن وُجد geo_level
    إن لم يوجد عضو مؤهّل → خطأ (قيد "توفّر أعضاء")
    chosen = العضو الوحيد تلقائياً، وإلا يُترك فارغاً للمستفيد
    أضِف خطوة (node, chosen, seq)
    node = node.parent_level_id
ألحِق المستويات العالمية (الأمين ولجانه) بالترتيب
اكتب route_ids على الطلب
```

- المستوى ذو العضو الواحد → **اختيار تلقائي**.
- المستوى متعدد الأعضاء → يُترك `documenter_id` فارغاً، ويختار المستفيد لاحقاً من
  قائمة المسار (مفلتَرة على أعضاء ذلك المستوى عبر `domain`).

### 3.2 التنفيذ — `doc.request`
الحالات: `draft → in_review → certified / rejected`.

| الزر/الإجراء | الشرط | الأثر |
|---|---|---|
| **Build Route** | draft | يفتح المعالج ويولّد `route_ids` |
| **Submit** (`action_submit`) | draft + مسار مكتمل، كل خطوة لها عضو | الحالة `in_review`، الخطوة الأولى `current`، تسجيل `submit`، إشعار أول عضو |
| **Approve / Escalate** (`action_approve`) | in_review، والمنفّذ هو عضو الخطوة الحالية | تسجيل `approve`، الخطوة `approved`، **التقدّم للعنصر التالي مباشرة فقط**؛ إن لم يبقَ تالٍ → `certified` |
| **Reject** (`action_reject`) | in_review، والمنفّذ عضو الخطوة الحالية | الحالة `rejected`، تسجيل `reject` |

التدفّق **من الأسفل للأعلى** عبر `parent_level_id` حصراً، والإشعار للعضو التالي
عبر `mail.activity` (todo).

### 3.3 القيود (المواصفة §12) — أين نُفِّذت
1. **منع التجاوز:** `action_approve` يتقدّم حصراً إلى `sequence` التالي في `route_ids`.
2. **تطابق العضو:** `_assert_current_actor` يمنع غير عضو الخطوة الحالية (إلا الأمين).
3. **اكتمال المسار:** `action_submit` يرفض أي خطوة بلا عضو مختار.
4. **توفّر أعضاء:** `_make_step` يرفض بناء مسار يمرّ بمستوى بلا عضو مؤهّل.
5. **تطابق العضو/المستوى:** قيد `_check_member_in_level` على خطوة المسار.

> ملاحظة انحراف بسيط: المواصفة تذكر حالة وسيطة `submitted` ثم `in_review`؛ التنفيذ
> ينتقل مباشرة إلى `in_review` عند الإرسال (الحالة `submitted` معرّفة لكنها غير
> مستخدمة كحالة استقرار). لا أثر وظيفي.

## 4. الواجهات (UI)

| الواجهة | المسار في القوائم | المحتوى |
|---|---|---|
| **باني الهرميات** | Certification → Builder → Hierarchies | نموذج الهرمية: النوع/الدولة + قائمة المستويات السطرية (الترتيب، الاسم، النوع، يتبع، الأعضاء) + زر **Clone to country** |
| **نموذج المستوى** | من داخل الهرمية | `kind`, `is_global`, `parent_level_id`, الجغرافيا، اللجنة، المنصب/القسم + الأعضاء السطريون (شخص، مستخدم، دور) |
| **المخطط التنظيمي** | Certification → Builder → Org Chart (Levels) | عرض **hierarchy** من الأعلى للأسفل (بطاقات بالاسم/النوع/عدد الأعضاء) |
| **الطلبات** | Certification → Requests | قائمة بالحالة الملوّنة + نموذج بأزرار سير العمل، شريط الحالة، تبويبات (المسار/الوثائق/سجل التدقيق)، ومحادثة `chatter` |
| **معالج بناء المسار** | زر داخل الطلب | اختيار مستوى الدخول → Build |

القوائم محميّة بالمجموعات: **Builder** للأمين/اللجنة فقط، و**Requests** للموثّقين فما فوق.

## 5. الصلاحيات والأمان (المواصفة §13)

المجموعات (تتوارث تصاعدياً): `beneficiary ⊂ documenter ⊂ committee ⊂ secretary`.

قواعد السجلات على `doc.request`:
- **المستفيد:** طلباته فقط (`citizen_id.user_ids = المستخدم`).
- **الموثّق:** طلباته + ما هو **العضو الحالي** فيه (`current_documenter_id.user_id = المستخدم`).
- **اللجنة/الأمين:** الكل (تفويض كامل).

النتيجة: عزل بين الدول والهرميات، ولا يرى الموثّق إلا ما أُسنِد إليه فعلاً.

## 6. كيف تُبنى أمثلة المواصفة في النظام

### مثال (أ) — هرمية قبلية، السعودية
أنشئ `doc.hierarchy`(النوع=قبلية، الدولة=السعودية)، ثم المستويات:

| seq | المستوى | kind | يتبع (parent) | الأعضاء |
|----|---------|------|---------------|---------|
| 10 | فرد قبلي | custom | مساعدو الشيخ الفرعي | (المقدّم — لا توثيق) |
| 20 | مساعدو الشيخ الفرعي | region | مشائخ القبائل الفرعية | أحمد، سعيد |
| 30 | مشائخ القبائل الفرعية | position | لجان شيخ المشائخ | محمد، عبدالعزيز |
| 40 | لجان شيخ المشائخ | committee | شيخ مشائخ الدولة | لجنة الرياض |
| 50 | شيخ مشائخ الدولة | position | *(عالمي تلقائياً)* | سعود |

المستويان 60/70 (لجان الأمين + الأمين) **عالميان مزروعان**، يُلحقهما باني المسار.
مثالا (ب) عُقّال و(ج) أقسام يُبنيان بنفس الطريقة بتغيير `kind`/الأعضاء فقط.

### تتبّع طلب (المواصفة §16)
مستفيد قبلي → اختار الهرمية القبلية → Build Route:
`20(أحمد/سعيد→يختار) → 30(محمد/عبدالعزيز→يختار) → 40(تلقائي) → 50(تلقائي) →
لجان الأمين(تلقائي) → الأمين(تلقائي)`. ثم Submit، وكل عضو يقبل بدوره حتى
`certified`. أي قفز مرفوض.

## 7. مقابلة معايير القبول (§17)

| المعيار | الحالة | أين |
|---|---|---|
| بناء هرمية كاملة بلا كود | ✅ | باني الهرميات/المستويات/الأعضاء |
| الخيار الهرمي في كل مستوى أياً كان نوعه | ✅ | `sequence`+`parent_level_id`+`documenter_ids` |
| اختيار العضو عند التعدّد وبناء المسار | ✅ | `doc.route.builder` |
| منع تجاوز المراحل | ✅ | `action_approve` + القيود |
| القمة المشتركة سجل واحد | ✅ | مستويات `is_global` المزروعة |
| ظهور الهرمية/العضو فوراً | ✅ | بيانات حيّة بلا كود |
| عزل تام + رؤية الموثّق المحصورة | ✅ | `ir.rule` |
| سجل تدقيق كامل | ✅ | `doc.request.log` + chatter |
| بوابة المستفيد على الويب | ⏳ مؤجّلة | "الخلفية أولاً" — تالية |

## 8. ما يحتاج تحقّقاً عند التشغيل
- توفّر `web_hierarchy` و`mail` (شرطا تثبيت).
- صحّة عرض **hierarchy** بصرياً، ومنطق **سير العمل** بطلب فعلي.
- بيانات السلّم القديم (إن وُجدت عيّنات) **لا تُرحَّل تلقائياً** — تُعاد بالباني الجديد.

## 9. القادم (مؤجّل بقرار "الخلفية أولاً")
بوابة المستفيد على الويب (اختيار هرمية → معالج المسار → رفع الوثائق → متابعة).
